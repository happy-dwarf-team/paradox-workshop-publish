# Prior art: Steam Workshop publishing actions and tools

Research for [#2](https://github.com/happy-dwarf-team/paradox-workshop-publish/issues/2). Checked on 2026-10-20 against the tools' own repositories (README, `action.yml`, source, issues, releases via `gh api`) and Valve's Steamworks documentation. "Verified" means read in source or official docs; "community" means a claim made in an issue or third-party write-up that we did not reproduce.

## Valve's ground rules

- `steamcmd +workshop_build_item <vdf>` takes a VDF with the keys `appid`, `publishedfileid`, `contentfolder`, `previewfile`, `visibility`, `title`, `description` and `changenote`. `publishedfileid` unset or `0` creates a new item, and on success steamcmd writes the new id back into the VDF. Valve says it "should only be used for testing purposes, as the tool requires the user to enter their Steam credentials". The documented keys do not include tags. ([Workshop implementation](https://partner.steamgames.com/doc/features/workshop/implementation))
- On ISteamUGC, items are created with `CreateItem` and uploaded with `SubmitItemUpdate`. Tags are set with `SetItemTags`. Items stay hidden until the contributor accepts the Workshop legal agreement (`m_bUserNeedsToAcceptWorkshopLegalAgreement`). ([Workshop implementation](https://partner.steamgames.com/doc/features/workshop/implementation))
- `SteamAPI_Init` fails if the Steam client isn't running, if the process runs under a different OS user from Steam, or if the active account has no licence for the App ID. ([Steam API overview](https://partner.steamgames.com/doc/sdk/api))
- Steam Guard on CI: Valve says to persist `<Steam>/config/config.vdf` between runs because it holds the login token. After the first login, runs should not pass the password, because a password login issues a new Steam Guard token. A denied login is fixed with `set_steam_guard_code`. ([Uploading to Steam](https://partner.steamgames.com/doc/sdk/uploading))
- GitHub warns against putting credentials in the Actions cache: "Anyone with read access can create a pull request on a repository and access the contents of a cache". PR runs can restore caches from the base branch, including from forks. ([Dependency caching](https://docs.github.com/en/actions/reference/workflows-and-actions/dependency-caching))

Notes, all verified in source unless marked otherwise:

- **Weilbyte.** The action has no inputs for title, preview, visibility or tags, and it cannot create an item: `itemid` is required ([action.yml](https://github.com/Weilbyte/steam-workshop-upload/blob/main/action.yml)). The Dockerfile pulls `steamcmd-2fa` from `releases/latest` without pinning a version ([Dockerfile](https://github.com/Weilbyte/steam-workshop-upload/blob/main/Dockerfile)). Open issue [#7](https://github.com/Weilbyte/steam-workshop-upload/issues/7) (2023) reports that the 2FA path fails because the binary renamed `--seed` to `--secret`, and the issue is still unresolved. Open issue [#5](https://github.com/Weilbyte/steam-workshop-upload/issues/5) shows `Failed to update workshop item (Invalid Parameter)` / "no workshop depot found" for one game. Weilbyte credits arma-actions/workshop-upload as its inspiration ([README](https://github.com/Weilbyte/steam-workshop-upload#readme)).
- **game-ci/steam-deploy, Steam Guard.** The released script decodes `configVdf` into `$STEAM_HOME/config/config.vdf`. It then runs a test login with `+set_steam_guard_code "$steam_totp" +login user pass` (the code is the string `INVALID` when no TOTP is given) and uploads with `+login user` and no password ([steam_deploy.sh@v3.2.1](https://github.com/game-ci/steam-deploy/blob/v3.2.1/steam_deploy.sh)). For TOTP, the README chains [CyberAndrii/steam-totp](https://github.com/CyberAndrii/steam-totp) with a `shared_secret` ([README](https://github.com/game-ci/steam-deploy#readme)). The README also documents the `config.vdf` refresh steps: `set_steam_guard_code`, plus re-exporting after a "License expired" error. Known problems: a base64 `config.vdf` can exceed the GitHub secret size limit, and the workaround is to gzip it first ([#77](https://github.com/game-ci/steam-deploy/issues/77)). Issue [#90](https://github.com/game-ci/steam-deploy/issues/90) (2026, community) is a Steam Guard prompt despite a valid `config.vdf`; it was closed as user error. On `main` the action downloads the `game-ci/cli` binary at `cliVersion: latest` by default ([action.yml](https://github.com/game-ci/steam-deploy/blob/main/action.yml), [download-cli.ts](https://github.com/game-ci/steam-deploy/blob/main/src/download-cli.ts)).
- **game-ci/cli `steam-workshop`** is the closest generic match. It treats a `PublishedFileId` line in the output as success, so an exit code of 0 alone is not enough ([parse-workshop-output.ts](https://github.com/game-ci/cli/blob/main/plugins/steam-workshop/src/parse-workshop-output.ts)). Gaps visible in the source:
  - It requires `STEAM_PASSWORD` and has no Steam Guard path.
  - It passes the password as a steamcmd argv entry, although the README claims credentials never go on the command line ([workshop-cmd-runner.ts](https://github.com/game-ci/cli/blob/main/plugins/steam-workshop/src/workshop-cmd-runner.ts), [README](https://github.com/game-ci/cli/blob/main/plugins/steam-workshop/README.md)).
  - It writes `workshop_build_item.vdf` inside the item folder, which is also `contentfolder`. We infer, without testing, that the VDF is uploaded with the mod.
  - Visibility defaults to `0` (public).
  - VDF values are not escaped ([steam-workshop-command.ts](https://github.com/game-ci/cli/blob/main/plugins/steam-workshop/src/steam-workshop-command.ts), [workshop-vdf-generator.ts](https://github.com/game-ci/cli/blob/main/plugins/steam-workshop/src/workshop-vdf-generator.ts)).
- **buildalon.** `setup-steamcmd` restores and saves `config/config.vdf` through `@actions/cache` under the key `steamcmd-config-<os>-<arch>` ([setup.ts](https://github.com/buildalon/setup-steamcmd/blob/main/src/setup.ts)). GitHub's docs say cached data can be read by anyone with read access who opens a PR, and steamcmd's login token is stored in that file ([GitHub](https://docs.github.com/en/actions/reference/workflows-and-actions/dependency-caching), [Valve](https://partner.steamgames.com/doc/sdk/uploading)). The generated Workshop VDF has only `appid`, `publishedfileid`, `contentfolder` and `description`, and `description` is used as the description rather than a change note ([upload.ts](https://github.com/buildalon/upload-steam/blob/main/src/upload.ts)).
- **Escaping.** None of the steamcmd tools above escapes `"` in VDF values. arma-actions has this as an open bug ([#1](https://github.com/arma-actions/workshop-upload/issues/1)).

All of these need a running, logged-in Steam client that owns the game ([Steam API overview](https://partner.steamgames.com/doc/sdk/api)), so none of them can run on a GitHub-hosted runner.

## Paradox-specific handling

- Only Yard1's action targets Paradox, and only HOI4 (`STEAM_APP_ID=394360`). It does so by running the Paradox launcher, so it needs a Paradox account and a POP3 mailbox ([action-entrypoint.sh](https://github.com/Yard1/pdx-steam-workshop-publisher-action/blob/master/lib/action-entrypoint.sh), [README](https://github.com/Yard1/pdx-steam-workshop-publisher-action#readme)). Its example prep script strips `picture=` from `descriptor.mod` ([PrepareForUpload.sh](https://github.com/Yard1/pdx-steam-workshop-publisher-action/blob/master/examples/PrepareForUpload.sh)). The repository is archived.
- None of the tools reads `descriptor.mod` or `metadata.json`, writes `remote_file_id`, maps descriptor tags to Workshop tags, or warns about checksums or achievements (verified in each source linked above).
- Tags can be set only through ISteamUGC (steamworks.js, nozwock, Darkborderman). steamcmd's documented VDF has no tags key ([Valve](https://partner.steamgames.com/doc/features/workshop/implementation)). Whether undocumented keys work is untested.

## Recommendation: build from scratch, borrowing patterns rather than code

- **Do not wrap or fork Weilbyte or arma-actions.** Both are stale, Linux/Docker-only, update-only and metadata-poor. Weilbyte's 2FA path is broken by an unpinned dependency (#7), and arma-actions has no licence.
- **Do not wrap game-ci.** `steam-deploy` uploads depots, not Workshop items. The `cli` Workshop plugin is two months old and experimental. It has no Steam Guard, puts the password in argv, uploads its own VDF and defaults to public. Depending on it would also pull a `latest` binary into our trust chain. Our core would be the Paradox layer (descriptor, `remote_file_id`, checksum warning, game profiles) plus a small steamcmd runner (game-ci/cli's is about 100 lines), which is less work than adapting theirs. Its bugs are worth reporting upstream, but that is optional and separate from v1.
- **Reuse these patterns:**
  - The Valve-documented `config.vdf` secret, in game-ci's form (`configVdf`, login without a password, refresh instructions, gzip when the secret is too large). Optional TOTP from `shared_secret` is an advanced path.
  - Success detection from `PublishedFileId`, as in game-ci/cli.
  - VDF escaping and private-by-default visibility, both lessons from the gaps above.
  - **Not** buildalon's Actions-cache storage of `config.vdf`.
- **Local mode:** keep the ISteamUGC binding behind an internal interface. steamworks.js 0.4.0 is proven in E3 and bundles the redistributables. Its npm stagnation (no `DeleteItem`, unreleased fixes, fork debate) is a risk to record in the local-mode ticket rather than a blocker, because deleting items is out of scope. steamworks-ffi-node is the active alternative, but users would have to obtain the SDK themselves.
