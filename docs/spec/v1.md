# paradox-workshop-publish v1 specification

Status: **accepted** by @s-tyda on 2026-10-20, including the points marked Proposed. It assembles the decisions on the [planning map](https://github.com/happy-dwarf-team/paradox-workshop-publish/issues/1); each section links the ticket that holds the reasoning. Terms in *italics* are defined in [GLOSSARY.md](../../GLOSSARY.md). Items marked **Proposed** were not decided in a ticket and are settled by accepting this document.

## 1. Purpose and scope

`paradox-workshop-publish` lets modders of Paradox Interactive games *publish* a *mod* to its *Workshop item* from GitHub Actions or from their own computer. It reads the game's own mod descriptor instead of a hand-written upload file. Its distinguishing features are Paradox-specific:

- descriptor-driven metadata;
- `remote_file_id` handling;
- a cleaned *published copy*;
- *checksum rules* that warn when a mod will cost players their achievements.

**Supported games (v1):**

| `game` | Game | Steam app | Descriptor profile |
| --- | --- | --- | --- |
| `eu4` | Europa Universalis IV | 236850 | `descriptor.mod` |
| `hoi4` | Hearts of Iron IV | 394360 | `descriptor.mod` |
| `stellaris` | Stellaris | 281990 | `descriptor.mod` |
| `imperator` | Imperator: Rome | 859580 | `descriptor.mod` |
| `ck3` | Crusader Kings III | 1158310 | `descriptor.mod` |
| `vic3` | Victoria 3 | 529340 | `.metadata/metadata.json` |
| `eu5` | Europa Universalis V | 3450310 | `.metadata/metadata.json` |

`ck2` is rejected with the message "CK2 uses legacy single-file Workshop items, which pdx-ws does not support" ([#19](https://github.com/happy-dwarf-team/paradox-workshop-publish/issues/19)).

**Out of scope for v1:**
- Paradox Mods;
- non-Paradox games;
- building or packaging mods;
- dedicated integrations for CI systems other than GitHub Actions;
- deleting items;
- localized titles and descriptions;
- Steam "required items";
- password + TOTP login.

## 2. Architecture

Sources: [#7](https://github.com/happy-dwarf-team/paradox-workshop-publish/issues/7), [ADR 0001](../adr/0001-rust-core-on-steamworks-rs.md), [ADR 0002](../adr/0002-create-items-in-client-mode.md).

- **One Rust core with the CLI `pdx-ws`**, built on `steamworks-rs`. The GitHub Action is a composite action that downloads a pinned, verified `pdx-ws` release binary. There is no Docker.
- **The *publish plan*** is computed purely from the repository: the mod, its *game profile* and `workshop.toml`. It holds:
  - the files of the published copy;
  - the Workshop metadata;
  - the target item ID;
  - the warnings;
  - the write-backs.
- **A *mode* executes the plan:**

  | Mode | How it reaches Steam | Where it runs | Can set |
  | --- | --- | --- | --- |
  | `steamcmd` | steamcmd with a *Steam session* from secrets | GitHub-hosted runners, any CI | content, title, description, preview, visibility, change note; **not tags** |
  | `client` | `ISteamUGC` through the logged-in Steam client | a modder's PC, self-hosted runners | everything above plus tags |

  Each mode declares its capabilities. The plan warns before publishing when the chosen mode cannot apply something; in `steamcmd` mode that happens when the release changes the descriptor's tags compared with the previous release tag, or with the previous commit when there is no tag. **Proposed:** the exact comparison point.
- **Item lifecycle:** a Workshop item is created once with `pdx-ws init` in `client` mode, and hosted CI then publishes releases in `steamcmd` mode (ADR 0002).

## 3. CLI

Source: [#8](https://github.com/happy-dwarf-team/paradox-workshop-publish/issues/8), [#9](https://github.com/happy-dwarf-team/paradox-workshop-publish/issues/9), [#20](https://github.com/happy-dwarf-team/paradox-workshop-publish/issues/20).

| Command | Does | Logs in |
| --- | --- | --- |
| `pdx-ws plan` | Prints the publish plan; sends nothing | Never |
| `pdx-ws publish` | Executes the plan in the chosen mode | Yes |
| `pdx-ws init` | Creates the item in `client` mode (private unless configured), writes its ID back | Yes (`client`) |
| `pdx-ws session export` | Installs steamcmd locally, runs the interactive login, prints the gzip + base64 *Steam session* **to stdout only** | Yes (interactive) |

Common flags:

| Flag | Meaning |
| --- | --- |
| `--config <path>` | Defaults to `workshop.toml` |
| `--mod <id>` | Repeatable; default is all mods |
| `--mode steamcmd\|client` | Defaults to `steamcmd` |
| `--change-note <text>` | Explicit change note |
| `--allow-create` | Lets `steamcmd` mode create an item |
| `--fail-fast` | Stop at the first failing mod |
| `--json` | Stable JSON output instead of text |

- **Credentials (Proposed).** In `steamcmd` mode the user name and the Steam session come only from the environment variables `PDX_WS_STEAM_USERNAME` and `PDX_WS_STEAM_SESSION`, never from argv. This avoids leaking them through the process list.
- **Exit codes (Proposed):**

  | Code | Meaning |
  | --- | --- |
  | 0 | Success; warnings allowed |
  | 1 | At least one mod failed to publish |
  | 2 | Configuration or validation error before any upload |
  | 3 | The Steam session is missing or expired. The message names `pdx-ws session export`. |

## 4. `workshop.toml`

Source: [#8](https://github.com/happy-dwarf-team/paradox-workshop-publish/issues/8), [#10](https://github.com/happy-dwarf-team/paradox-workshop-publish/issues/10), [#11](https://github.com/happy-dwarf-team/paradox-workshop-publish/issues/11), [#20](https://github.com/happy-dwarf-team/paradox-workshop-publish/issues/20).

```toml
schema = 1

[defaults]                       # optional; any [[mod]] key except id, path, item_id
game = "eu4"
checksum = "warn"

[[mod]]
id = "my-mod"                    # required only with several mods
game = "eu4"                     # required (here or in [defaults])
path = "."                       # default "."
visibility = "private"           # unset: publish never changes visibility
exclude = ["docs/**"]            # globs, combined with defaults and built-ins
description = "workshop/description.md"   # .md (converted) or .bbcode (verbatim)
changelog = "CHANGELOG.md"
checksum = "warn"                # "warn" | "keep" | "ignore"; EU4 only in v1
# item_id = 123                  # metadata.json games only
```

- **Strict keys.** Unknown keys are errors, and so is a missing `schema`. A value in `[[mod]]` overrides `[defaults]`; `exclude` lists are combined.
- **`visibility`** is one of `public`, `friends`, `private`, `unlisted`.
  - `init` uses it, or `private` when unset.
  - `publish` sends visibility only when the key is set.

## 5. Game profiles and metadata

Source: [#4](https://github.com/happy-dwarf-team/paradox-workshop-publish/issues/4), [#8](https://github.com/happy-dwarf-team/paradox-workshop-publish/issues/8).

- **Metadata comes from the descriptor only**, with no overrides in v1:

  | Workshop field | `descriptor.mod` profile | `metadata.json` profile |
  | --- | --- | --- |
  | Title | `name` | `name` |
  | Tags | `tags`, sent verbatim (Steam keeps undeclared tags and fixes their case) | `tags`, sent verbatim |
  | Preview | `thumbnail.png` in the mod root | `.metadata/thumbnail.png` |
  | Version (for change notes) | `version` | `version` |

  Tags are applied in `client` mode only. A preview of 1 MB or more is a validation error.
- **Optional plan warnings:** tags outside the game's declared Workshop list, and the documented launcher limits (Stellaris 10 tags, Victoria 3 5 tags).
- **Item ID:**
  - The source of truth is `remote_file_id` in `descriptor.mod`, or `item_id` in `workshop.toml` for `metadata.json` games. A conflict between the two is an error.
  - `init` writes the ID back, and the modder commits it. CI never commits.
  - Without an ID, `publish` in `steamcmd` mode fails with "run `pdx-ws init` in `client` mode first", unless `--allow-create` is given; that creates an item without tags and prints its ID.

## 6. Published copy

Source: [#8](https://github.com/happy-dwarf-team/paradox-workshop-publish/issues/8).

Every publish copies the mod to a temporary folder:
- **Excluded:** `.git*`, `.github/`, `workshop.toml`, `*.vdf`, and the configured `exclude` globs.
- **`descriptor.mod` in the copy:**
  - loses `path`, `archive` and `user_dir`;
  - gains `remote_file_id`;
  - is rejected if it has a BOM.

The only change in the repository is the ID written back by `init`.

## 7. Description and change notes

Source: [#11](https://github.com/happy-dwarf-team/paradox-workshop-publish/issues/11).

- **Description:**
  - `.md` files are converted from Markdown to Steam BBCode. Supported: `[h1]`–`[h3]`, bold, italic, strikethrough, links, lists, quotes, code, horizontal rules and tables. A line break inside a paragraph stays a line break, as in GitHub comments, and paragraphs are separated by a blank line. Headings, lists and image-only lines are separated from their neighbours by a single newline, except for a blank line before a heading that follows text or a list, as on the team's hand-written Workshop pages. Raw HTML, footnotes and relative image paths are errors that name the line.
  - `.bbcode` files are sent verbatim.
  - The limit is 8000 characters after conversion.
  - Without `description`, the Workshop description is never touched. With it, every publish overwrites the description, and `plan` says so.
- **Change note precedence:**
  1. An explicit `--change-note` or `change-note`.
  2. The `changelog` section for the descriptor version. release-please (`## [1.2.0](…)`) and Keep a Changelog (`## [1.2.0] - …`) headings are recognised. A configured changelog without that section is an error.
  3. `Version <version>`, plus the commit URL in CI.

  The change note goes through the same converter. Then it is tidied for players:
  - headings become bold lines, a version heading becomes **Version x.y.z**, and Features, Bug Fixes and Performance become New, Fixes and Faster;
  - release-please's links to pull requests, issues and commits are dropped;
  - list items start with a capital letter;
  - a changelog section gets **Version x.y.z** first.
- **Verification:** no extra post-publish check. The mode's success signal counts, and `plan` shows the rendered BBCode.

## 8. Checksum warning

Source: [#5](https://github.com/happy-dwarf-team/paradox-workshop-publish/issues/5), [#10](https://github.com/happy-dwarf-team/paradox-workshop-publish/issues/10).

- **Scope.** EU4 only in v1, with *checksum rules* verified on 1.37.5. For other games `plan` says the check is not available. A game is enabled only after its rules are verified on a real install.
- **Predicate.** A mod changes the checksum when:
  - any file in the published copy matches a rule (folder, recursion, extension, excludes); or
  - a `replace_path` covers checksummed scope. [E5](https://github.com/happy-dwarf-team/paradox-workshop-publish/issues/21) confirmed this for EU4 1.37.5, even when the mod ships no file there.

  Byte-identical vanilla files are a known false positive.
- **`checksum` setting:**

  | Value | Behaviour |
  | --- | --- |
  | `warn` (default) | Annotation and plan entry |
  | `keep` | A checksum change fails the publish |
  | `ignore` | Silent |
- **Output.**
  - The matching paths are listed (about 15, then "and N more").
  - For EU4 the wording is: "players lose achievements while this mod is enabled, and multiplayer partners need the same mods; ironman itself still works".
  - The tool never says "achievements are kept".
- **Data.**
  - Rules use our own format and are embedded in the binary, with the game version, "verified on" and a source.
  - They are selected by `supported_version`. With no match the newest table is used, and the plan says so.
  - In `client` mode, when the game is installed, the installed `checksum_manifest.txt` is read and any drift from the table is reported.

## 9. `steamcmd` mode

Sources: [#3](https://github.com/happy-dwarf-team/paradox-workshop-publish/issues/3), [#6 (E4)](https://github.com/happy-dwarf-team/paradox-workshop-publish/issues/6), [#9](https://github.com/happy-dwarf-team/paradox-workshop-publish/issues/9).

- **Setup.**
  - steamcmd is downloaded from Valve's CDN into `RUNNER_TEMP` or a temporary folder. The binary may use the runner's tool cache; the session never does.
  - On Linux the mode installs `lib32gcc-s1`. On Windows the self-update's exit code 7 is accepted.
- **Session.**
  - The decoded session goes to the steamcmd folder's `config/config.vdf`, or to `~/Steam/config/config.vdf` on Linux.
  - Login uses `+login <user>` only, with stdin closed and a timeout.
  - The rotated session file is never written back.
- **VDF.**
  - It is written outside the published copy.
  - Values are escaped (`\` and `"`).
  - It holds only the keys the plan sets: `appid`, `publishedfileid`, `contentfolder`, plus `previewfile`, `title`, `description` and `visibility` when set, and `changenote`.
- **Results** (observed in E4):
  - Success is `Committing update...Success.` together with the ID written back into the VDF.
  - Exit code 9 means a build failure, e.g. `ERROR! Build for workshop item has no content`.
  - Exit code 5 with `Cached credentials not found` or `Invalid Password` means the session is missing or expired (CLI exit 3).
  - `depot_build_<appid>.log` and `workshop_log.txt` are summarised on failure, and shown in full after a success.
  - **No content change** ([#39](https://github.com/happy-dwarf-team/paradox-workshop-publish/issues/39), E2E run 39497323643): when the published copy equals the item's current content, steamcmd prints the same `Success` lines, but `workshop_log.txt` says `No content change detected for item <id>` and the depot log `Success! Previous manifestID <id> reused, no chunks uploaded.` Steam then keeps the version and does not record the change note. The mod's result is `unchanged`, with a warning (and an annotation in the action); it exits 0. A new version logs `Uploaded new content ( ManifestID <id> )` and `Success! New manifestID <id> created`.
- **Hygiene.**
  - The session is never printed.
  - SteamIDs in output are replaced with `[U:1:***]`.
  - The session file and the steamcmd folder are deleted at the end, including on failure.

## 10. `client` mode

Sources: lab experiment E3, [#7](https://github.com/happy-dwarf-team/paradox-workshop-publish/issues/7), [#13](https://github.com/happy-dwarf-team/paradox-workshop-publish/issues/13).

- **Steam API.** Uses `steamworks-rs` against the running Steam client with the game's app ID. The account must own the game and the item. `SteamAPI_Init` fails if Steam is not running or runs as another OS user.
- **`init`:**
  - calls `CreateItem` and checks `needsToAcceptAgreement`; if it is true, the tool prints the Workshop legal agreement URL;
  - sets content, title, tags, preview, visibility (default `private`) and the description;
  - writes the ID back.
- **`publish`:** does the same as `init` for an existing item, tags included.
- **Progress:** reported from `GetItemUpdateProgress`.
- **Checksum check:** reads the game install folder from Steam for the checksum cross-check.

## 11. GitHub Action

Sources: [#8](https://github.com/happy-dwarf-team/paradox-workshop-publish/issues/8), [#9](https://github.com/happy-dwarf-team/paradox-workshop-publish/issues/9), [#18](https://github.com/happy-dwarf-team/paradox-workshop-publish/issues/18).

| Inputs | Default | Outputs |
| --- | --- | --- |
| `mode` | `steamcmd` | `item-id` |
| `config` | `workshop.toml` | `item-url` |
| `mod` | all | `plan-json` (path) |
| `steam-username` | — | |
| `steam-session` | — | |
| `change-note` | — | |
| `dry-run` | `false` | |
| `pdx-ws-version` | the action's own tag | |

With several mods, `item-id` and `item-url` hold the selected mod or are empty, and `plan-json` holds all mods (Proposed).

**Behaviour:**
- **Binary download.** The action downloads the release archive for the runner OS and verifies it with `gh attestation verify`. Without `gh` it checks the SHA-256 sums file and warns.
- **Credentials.** It passes credentials to `pdx-ws` through environment variables only.
- **Pull requests.**
  - On `pull_request` events it always runs as `dry-run`.
  - On `pull_request_target` it refuses to run.
- **Reporting.** It writes a job summary (plan table, per-mod results, item links, rendered description and change note, checksum findings) and an annotation for each warning, file-level for checksum matches.
- **Cleanup.** A post step deletes the session even after failures.

**Example workflows** shipped in the docs:
1. Single mod, publishing on a published GitHub Release with `change-note: ${{ github.event.release.body }}`. It uses a `steam-workshop` environment with secrets; required reviewers are recommended.
2. A `pull_request` workflow running `dry-run` as a preview.
3. Multi-mod with release-please monorepo tags `<id>-vX.Y.Z`.

## 12. Security model and user documentation

Source: [#9](https://github.com/happy-dwarf-team/paradox-workshop-publish/issues/9), [#13](https://github.com/happy-dwarf-team/paradox-workshop-publish/issues/13).

The user docs include a **risk section**:
- **What the Steam session can do:** log in to steamcmd as the modder to publish, update and download. It does not reveal the password or the second factor.
- **How to revoke it:** "Deauthorize all devices" in Steam Guard, or change the password.
- **Recommendations:** keep the secrets in an environment, publish only on tags or releases, and renew the session when collaborators change.
- **`client` mode on self-hosted runners:** private repositories only, because any workflow on that runner can publish as the logged-in Steam user.
- **The Steam Subscriber Agreement §4.C "Automation" clause:** its examples do not cover Workshop publishing, and Valve documents steamcmd for CI uploads. The docs state this neutrally and leave the judgement to the modder.

There is also a **self-hosted runner recipe for `client` mode**: a dedicated OS user logged in to Steam, the runner service as that user, and a private repository.

## 13. Releases and testing

Source: [#18](https://github.com/happy-dwarf-team/paradox-workshop-publish/issues/18), [#13](https://github.com/happy-dwarf-team/paradox-workshop-publish/issues/13).

**Versioning:**
- One version and one tag `vX.Y.Z` for `pdx-ws` and the action, managed by release-please.
- Releases start at `0.1.0`. `1.0.0` comes once v1 is implemented and used on our own mods.
- From 1.0 there is also a floating `v1` tag.

**Release archives:**
- `cargo-dist` builds Windows x64, Linux x64 and macOS (arm64 + x64).
- Each archive holds the binary, the platform's `steam_api`, `LICENSE` and `THIRD_PARTY_NOTICES`.
- Every release has SHA-256 sums and artifact attestations.

**Steamworks:**
- @s-tyda is the Steamworks SDK Licensee.
- The release build checks the `steam_api` hashes against the official SDK.

**Marketplace:** the listing starts at 1.0.

**Tests:**
- **Every PR:** fixture mods (EU4, Vic3, EU5, with and without `remote_file_id`), BBCode, VDF, checksum rules, and a **fake steamcmd** that replays E4's real outputs.
- **End to end:** a private test item on @s-tyda's account in a `steam-workshop-e2e` environment with required approval. It runs on release-please release PRs and on manual dispatch, publishes in `steamcmd` mode on Ubuntu and Windows, and compares the downloaded files.
- **`client` mode:** a manual pre-release checklist.
